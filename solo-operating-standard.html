RULE 01

Write the rule the day it breaks

What broke

You fix something, learn something real, and three weeks later the identical bug bites in a different corner of the same project. The lesson was never written down — it lived in your head, or worse, in a chat window that closed.

Working with AI makes this sharper. "How we do things here" doesn't survive the end of a conversation. The next session starts from nothing — confidently.

The rule

Every lesson becomes a written rule, in a file, the same day you learn it — and the rule carries the incident that caused it. A rule without its origin story gets deleted by a future you who doesn't know what it cost.

The prompt · run once to start your rulebook 
Help me start an operating standard for this project.

Ask me one question at a time about the last three things
that broke here — what happened, what it cost me, how I
found it.

For each one, write a short rule file containing:
  1. The incident, with the date
  2. The rule that would have prevented it, stated as an
     instruction you could follow literally
  3. How to run it — the concrete check, not the principle

Save them as rules/<short-name>.md, one file per rule.
Do not invent rules for failures I haven't actually had.
How to run it

Point your AI tool at that folder in its instructions file so the rules load automatically, every session, without you remembering to mention them. A standard nobody reads is a document; a standard your tools read is a system.

RULE 02

Prove it exists before you touch it

What broke

An AI will confidently reference a function that doesn't exist, a database column nobody created, a route nobody registered. It isn't lying — it's pattern-matching from a thousand codebases that did have those things. The code looks perfect. It fails the moment it runs.

Humans do the same thing. You just do it slower, so you catch yourself more often.

The rule

Before writing a line: prove the file exists, prove every function and endpoint you're calling exists, prove every database column you're writing to is really in the schema, and prove any new route is actually registered. If you can't prove it exists, you don't touch it.

The prompt · paste before any coding task 
Before you write any code for this task, run a reality check
and show me the results:

  - List the exact files you plan to change, and confirm each
    one exists by reading it. Not from memory.
  - For every function, component, or endpoint you'll call,
    show me where it is defined.
  - For every database field you'll write to, show me the
    schema line that proves it exists.
  - If this adds a route, show me where routes get registered
    and confirm yours is there.

If you cannot verify any one of these, STOP and tell me which
one — do not proceed on an assumption.
How to run it

Put it in your tool's instructions so it happens unprompted. The few seconds it takes to open a file is the cheapest insurance in software.

A green build is not proof the bug is fixed.

RULE 03

"Done" is a claim about verified reality

What broke

Twice in two days I was handed work reported as finished that wasn't. The first blamed a failure on caching — it wasn't caching, and an unverified change went to production behind that theory. The second claimed a design had been built to spec when large parts of it hadn't been built at all.

Neither was malicious. Both were intentions reported as outcomes. And the cost of that lands entirely on whoever discovers it later — which is you, or your client.

The rule

Done, fixed, working and shipped are claims about verified reality. State the evidence beside the claim, every time. Fixed a bug? Show the reproduction now failing to reproduce. Can't verify it yourself? Say "built, not verified — here's the one thing to check." Never round unverified up to done.

The trap underneath it

A convenient cause is not a diagnosis. "It's probably the cache" is a hypothesis until evidence says otherwise. Pull the real signal — the log line, the actual status code, the error text — and quote it before naming a cause. On a "page won't load," get the status first: a 200 means the server is fine and you've been debugging the wrong layer.

And build-clean is not runtime-clean. A tidy-up once left a variable deleted in one place and still referenced in another. Valid syntax. Clean build. 200 response. It threw the instant someone clicked. If a change is interactive, execute the path before calling it done. "It compiled" is not "I saw it work."

The prompt · paste when you're told something is finished 
Before you tell me this is done, give me a completion report:

  1. WHAT YOU CHANGED — files, and what each change does.
  2. THE EVIDENCE — what you actually observed proving it
     works. A passing build does not count. Quote the log
     line, the response, or the state you saw.
  3. WHAT YOU DID NOT DO — anything skipped, assumed, or
     left half-finished.
  4. WHAT I MUST CHECK MYSELF — anything you could not
     verify (needs a login, real data, a real device).

If you cannot produce section 2, say "built, not verified"
instead of "done". Do not describe intentions as outcomes.
RULE 04

The same thing must not live in two places

What broke

One product, one afternoon, eight instances of the same structural mistake. Not logic errors — duplication. The same rule written twice, drifting quietly apart.

What users actually saw: a score of 60 rendering amber on one screen and red on another, because four copies of the same grading ladder had drifted apart. A reordered sentence painted as a total rewrite, because two files each decided "what changed" their own way. And the worst one — the document a user could edit was not the document they were being scored on.

Every one of them was invisible until a real person hit it. Several had been wrong for weeks.

The rule

Before writing a second implementation of anything a user sees, stop. Same logic in two places → collapse it into one; "they're identical today" is the state every drift starts from. Same value on two surfaces → compute it once and carry it, with a note of where it came from and a check that its inputs haven't changed since.

The prompt · run on any codebase more than a few months old 
Audit this codebase for duplicated logic that users can see.

Look specifically for:
  - The same threshold or cutoff number written in more than
    one file (a score, a limit, a price tier)
  - Comments containing "keep in sync", "mirrors", or
    "same as" — each one is a promise no code is keeping
  - The same calculation or formatting implemented twice
  - The same value stored in two places without one being
    clearly derived from the other

For each finding, report:
  WHAT is duplicated · WHERE each copy lives · WHAT A USER
  WOULD SEE if the copies disagreed by one step.

Rank by user-visible impact. Don't fix anything yet.
How to run it

When you fix one, test the wiring, not just the shared function — a unit test on the helper won't catch a caller that quietly stopped using it. Then put the bug back on purpose and watch the test go red. A guard you've never seen fail is a guard you're guessing about.

A cost you can't see is a liability, because it grows without anyone choosing it.

RULE 05

Unmeasured is worse than expensive

What broke

I audited my hosting bill, found the waste, and felt responsible. Then I looked at a second vendor. The real monthly number was substantially higher than the one I'd just "fixed" — the AI spend on a single product was nearly half of everything I'd been congratulating myself on. Of the projects making AI calls, exactly one was logging what it spent.

The rule

Never report an unmeasured cost as zero. It's "no number" — never $0. Rounding an unknown down to zero is how a bill becomes a surprise. Label every figure: measured (from a bill), estimated (price × observed volume), or unmeasured (we know it bills; we don't know what).

The prompt · the audit that found mine 
Find every place this project spends money per-use.

For each one, report:
  - Where the call is made (file and line)
  - Which vendor and which model or service
  - Whether the cost of that call is logged anywhere I could
    query later — and if not, say UNMEASURED, never $0
  - Whether it is rate-limited or capped, and what happens
    if someone calls it in a loop

Then list every free tier this project depends on and how
close it is to its ceiling. A hit ceiling is an outage, not
a bill.

Flag the quiet ones explicitly: anything billed per-character
or per-second (speech, audio, video) can outspend text by an
order of magnitude while looking harmless in a diff.
How to run it

Log the cost of a paid call in the same commit that adds the call — never in a "hardening pass" later, because that pass is exactly what doesn't happen. And know your cost per user before you set a price: on anything usage-based, a low price means your most engaged users are your least profitable, and you find that out after launch.

RULE 06

Start and end every session the same way

What broke

Working with AI turns your written records into the memory. So the failure mode isn't forgetting — it's confidently remembering wrong. I had a status file claiming a catalog held 126 items on a day it actually held 234. The correct number was in the code the whole time. The file wasn't even old; it had been updated that same day. It just wasn't true anymore.

The rule

Start: read your notes, then reconcile them against what the code and commit history actually say. If the notes and the commits disagree, the commits win — flag the gap, don't paper over it. End: write back what shipped, what's open, and what's next, before the session closes. A session that never ends never wraps.

The prompt · paste at the start of every session 
Before we start work, get oriented and tell me the truth:

  1. Read my project notes and status files.
  2. Read the recent commit history.
  3. Compare them. Where the notes and the commits disagree,
     the commits win — list every discrepancy you find
     instead of quietly going with the notes.
  4. Check any number in my notes (counts, versions, totals)
     against the code it describes. Recently written is not
     the same as still true.

Then give me: what is actually true right now, what my notes
claim that isn't, and what you think the next task is.
The prompt · paste before you close the session 
Wrap this session:

  1. Write a log entry — what shipped, the evidence for each
     claim, decisions made, what's still open.
  2. Update my status file so it reflects reality as of now.
     Regenerate it; don't patch the old numbers.
  3. Run the build/test check and report the real result.
  4. List what I should pick up first next time.

Be honest about anything half-finished. A wrap that hides a
loose end just moves the cost to next week.
How to run it

Keep sessions bounded — one arc each: an evening, a feature, a bug-hunt. Long sessions accumulate context that lives nowhere but the conversation, and it dies with them. If a fresh session comes back confused, your records drifted. That's a finding, not an inconvenience.

WHERE TO START

Pick the one whose failure you've already had

Don't adopt six rules on a Monday.

  • Shipped a fix you never actually confirmed → Rule 03
  • Two screens showing different numbers for the same thing → Rule 04
  • No idea what your AI usage costs this month → Rule 05
  • Come back to a project and can't tell what's true → Rule 06

Run that one prompt today. Write the rule it produces. Add the next one the next time something breaks.

That's the whole method. The standard isn't something you design in advance — it's the accumulated record of everything that's already gone wrong, written down before you forget what it cost.
